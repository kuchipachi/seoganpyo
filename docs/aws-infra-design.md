## 1. 네트워크 — 왜 퍼블릭 서브넷만 쓰나

### 교과서 구성

```
Internet ─> IGW ─> [퍼블릭 서브넷] ALB ─> [프라이빗 서브넷] EC2 ─> RDS
                                    └─> NAT Gateway (EC2의 아웃바운드용)
```

DB와 앱 서버를 프라이빗 서브넷에 두고, 외부 노출은 ALB만. 이게 일반적인 권장 구성입니다.

### 우리 구성

```
Internet ─> IGW ─> [퍼블릭 서브넷]
                      ├── EC2 (Caddy + 앱 컨테이너)  ← 공인 IP 있음
                      └── RDS (퍼블릭 액세스 OFF)    ← 공인 IP 없음
```

### 이유 — 비용

| 리소스 | 월 비용 | 우리 선택 |
| --- | --- | --- |
| ALB | ~$16 | **Caddy on EC2** |
| NAT Gateway | ~$32 | 퍼블릭 서브넷만 사용 |

크레딧이 $120~200이고 6개월 기한입니다. 이 둘만 만들어도 **월 $48 — 크레딧의 약 25%**가 매달 사라집니다.

### 프라이빗 서브넷을 쓰면 NAT가 왜 필요한가

프라이빗 서브넷의 인스턴스는 **공인 IP가 없어서 인터넷으로 나갈 수 없습니다.** 그런데 우리 EC2는 나가야 합니다:

- `docker pull` (ECR, Docker Hub)
- `apt-get update`
- Mistral·Gemini API 호출
- Grafana Cloud remote write
- `cs.sogang.ac.kr` 크롤링

나가려면 NAT Gateway가 필요하고, 그게 월 $32입니다. **그래서 EC2를 퍼블릭 서브넷에 둡니다.**

### 그럼 보안은 어떻게 지키나

퍼블릭 서브넷에 있다는 건 "공인 IP가 있다"는 뜻일 뿐, "누구나 들어올 수 있다"는 뜻이 아닙니다.
**실제 차단은 보안그룹이 합니다** (§2).

```
퍼블릭 서브넷  =  공인 IP 할당 가능 + IGW 라우팅 있음
보안그룹      =  실제로 어떤 트래픽을 받을지 결정
```

즉 서브넷은 "주소가 있느냐", 보안그룹은 "문을 열어주느냐"입니다. 우리는 주소는 주고 문은 3개만 엽니다.

### 트레이드오프 — 포기한 것

| 항목 | 영향 |
| --- | --- |
| 다중 AZ 이중화 | EC2 1대·RDS 단일 → AZ 장애 시 서비스 중단 |
| 네트워크 계층 방어 | 서브넷 격리가 없어 보안그룹이 유일한 방어선 |
| 오토스케일링 | ALB가 없어 수평 확장 불가 |

포트폴리오·학습 목적이고 SLA가 없으므로 감수합니다. **실무라면 ALB·NAT를 쓰는 게 맞습니다.**

## 2. 보안그룹 — 설계의 핵심

### 기본 개념

보안그룹은 **인스턴스 단위 방화벽**입니다. 두 가지 성질을 알아야 설계가 이해됩니다.

| 성질 | 의미 |
| --- | --- |
| **화이트리스트** | 명시적으로 허용한 것만 통과. Deny 규칙이 없습니다 |
| **스테이트풀** | 인바운드로 들어온 요청의 응답은 아웃바운드 규칙과 무관하게 자동 허용 |

스테이트풀이라는 점이 중요합니다. `SG-rds`에 아웃바운드 규칙을 따로 안 넣어도, EC2가 보낸 쿼리에 대한 **응답은 자동으로 돌아갑니다.**

### `SG-web` — 3줄

| 유형 | 포트 | 소스 | 왜 |
| --- | --- | --- | --- |
| HTTP | 80 | `0.0.0.0/0` | 누구나 접속. Caddy가 HTTPS로 리다이렉트 |
| HTTPS | 443 | `0.0.0.0/0` | 실제 서비스 트래픽 |
| SSH | 22 | `175.210.215.211/32` | **본인 IP만** — 서버 관리용 |

**"모든 트래픽 + 내 IP"로 하면 안 되는 이유**

처음에 그렇게 설정했다가 고쳤습니다. 그 구성은 정확히 반대입니다:

- 웹 서비스인데 하연 IP에서만 접속 가능 → 민지·시연 참석자 접속 불가
- 들어오면 모든 포트 개방 → Redis(6379), 백엔드(8000) 등이 그대로 노출

**웹은 전체 공개, 관리 포트는 본인만**이 원칙입니다.

> ⚠️ `175.210.215.211`은 **가정용 동적 IP**입니다. 공유기 재부팅·망 이동 시 바뀌고,
> 그러면 SSH가 막힙니다. 카페·학교에서 작업하면 매번 규칙을 갱신해야 합니다.
>
> → 2차에 **SSM Session Manager**를 도입하면 22번 포트를 아예 닫을 수 있습니다.
> 계획서 §7의 "SSH 없는 배포"와 같은 방향입니다.

### `SG-rds` — 1줄, 그런데 핵심

| 유형 | 포트 | 소스 |
| --- | --- | --- |
| PostgreSQL | 5432 | **`sg-095b42d816c449f1b`** (= `SG-web`) |

소스가 **IP가 아니라 보안그룹 ID**입니다. 이게 이 설계에서 가장 중요한 부분입니다.

```
[인터넷]  ──✕──>  RDS        (퍼블릭 액세스 OFF — 공인 IP 자체가 없음)
[EC2]     ──✓──>  RDS        (SG-web 멤버이므로 허용)
[다른 EC2]──✕──>  RDS        (SG-web 멤버가 아니면 거부)
```

**IP로 쓰지 않은 이유**

| 방식 | 문제 |
| --- | --- |
| `10.0.1.0/24` (서브넷 CIDR) | 그 서브넷의 **모든** 인스턴스가 DB 접근 가능 |
| EC2 사설 IP 고정 | EC2 재생성 시 IP가 바뀌어 규칙을 매번 수정 |
| **보안그룹 참조** | EC2가 바뀌어도 `SG-web`만 붙어 있으면 자동 적용 ✅ |

보안그룹 참조는 **"이 그룹에 속한 것만"** 이라는 논리적 조건이라, 인프라가 바뀌어도 규칙을 고칠 필요가 없습니다.

### 왜 SG를 2개로 나누나

하나로 합치면 이렇게 됩니다:

```
SG-all: 80, 443, 22, 5432 허용
        → EC2와 RDS가 같은 그룹
        → 5432가 어디서 들어오는지 통제 불가
```

**역할별로 나누면 "누가 누구에게 접근하는지"가 규칙 자체에 드러납니다.** 나중에 Redis를 별도 인스턴스로 빼거나 컨테이너를 늘려도 같은 패턴으로 확장됩니다.

## 3. RDS 설정 — 항목별 근거

| 항목 | 값 | 근거 |
| --- | --- | --- |
| 엔진 | PostgreSQL | 기존 스키마가 PostgreSQL. SQLAlchemy 모델 그대로 사용 |
| 템플릿 | **프리 티어** (고정) | 무료 플랜은 선택 불가 — Multi-AZ가 아예 막혀 오히려 안전 |
| 클래스 | `db.t4g.micro` | ARM(Graviton)이 x86보다 저렴. 월 ~$15 |
| Multi-AZ | **끄기** | 켜면 비용 2배. 학습 목적엔 불필요 |
| 스토리지 | gp3 20GB | 최소값. 현재 데이터는 `static/` 884KB + 테이블 몇 개 |
| **자동 조정** | **끄기** | 켜두면 모르는 새 늘어나 크레딧 소진 |
| **퍼블릭 액세스** | **아니요** | 공인 IP 미할당 → 인터넷에서 도달 자체가 불가 |
| 보안그룹 | `SG-rds` | 기본 SG 해제 필수 |
| 백업 보존 | **1일** | 무료 플랜 상한. 7일 설정 시 오류 |
| Performance Insights | **끄기** | 장기 보존 시 유료 |
| 서브넷 그룹 | 기본값 | Default VPC의 4개 서브넷 (4 AZ) |

### 퍼블릭 액세스 OFF의 의미

"DB에 공인 IP를 주지 않는다"는 뜻입니다. 보안그룹 규칙과 **별개의 층**입니다.

```
퍼블릭 액세스 ON  + SG로 차단   →  IP는 있지만 문이 닫힘 (실수 한 번에 열림)
퍼블릭 액세스 OFF + SG로 차단   →  IP가 없어서 애초에 도달 불가 ✅
```

두 겹으로 막는 게 맞습니다. SG 규칙을 실수로 `0.0.0.0/0`으로 바꿔도, 공인 IP가 없으면 외부에서 못 옵니다.

### 백업 1일 제약 — §2.5 훈련 방식 변경

무료 플랜은 자동 백업 보존이 최대 1일입니다. 계획서 §2.5는 7일 기준이었는데 수정이 필요합니다.

| 기존 계획 | 수정 |
| --- | --- |
| 자동 백업 7일 → 시점 복구(PITR) | **수동 스냅샷 생성 → 복원** |

**수동 스냅샷은 보존 제한이 없습니다.** 훈련의 핵심(스냅샷 → 새 인스턴스 → 데이터 검증 → 삭제)은 그대로 가능하고, "백업·복구 절차 검증"이라는 항목에는 오히려 더 명시적입니다.

> ⚠️ 복원은 **새 인스턴스를 만듭니다.** 검증 후 즉시 삭제하지 않으면 크레딧이 2배로 깎입니다.

### 구성

| 항목 | 값 | 근거 |
| --- | --- | --- |
| 인스턴스 ID | `i-0cf5fbf562ec4017b` | |
| 타입 | **`t3.micro`** (2 vCPU / 1 GiB) | 크레딧 절약. IAM Deny 정책이 다른 타입 차단 |
| AMI | `ami-03137ee2d0c5af1fe` (Amazon Linux 2023) | `dnf` 기반, Docker 공식 패키지 제공 |
| 서브넷 | 퍼블릭 (`vpc-009480d192b44ba23`) | NAT Gateway 회피 (§1) |
| 보안그룹 | `SG-web` | 80/443 공개, 22 본인 IP만 (§2) |
| 스토리지 | gp3 30GB | 기본 8GB로는 Docker 이미지 3개가 안 들어감 |
| EIP | `54.180.181.46` (`eipalloc-0653b7b300fe910fb`) | 재부팅 시 IP 고정 |
| 키 페어 | `server-key` | |

### 메모리 — 이 프로젝트의 핵심 제약

```
Mem:   913Mi   (실측 — 1GiB 중 커널이 일부 점유)
Swap:  1.5Gi   (Amazon Linux 2023 기본 제공)
────────────────────────────────────────────
가용:  약 2.4GB
```

여기에 컨테이너 5개(`frontend` `backend` `ocr` `redis` `caddy`)를 올려야 합니다.
기존 `docker-compose.yml`의 **메모리 예약 합계가 이미 1GB**라 그대로 쓰면 OOM이 납니다.

| 시점 | 조치 |
| --- | --- |
| D4 (🟩 민지) | 예약 하향 — backend 256M / frontend 256M / ocr 192M |
| D4 (🟩 민지) | `NODE_OPTIONS=--max-old-space-size=256` |
| D7~D8 (🟪 페어) | 부하를 걸며 실측 튜닝 → 포스트모템 (§2.2, §8.4) |

> ⚠️ **프론트엔드 빌드를 EC2에서 하지 않습니다.** `pnpm build`는 1GB에서 거의 확실히 OOM입니다.
> 맥북에서 `--platform linux/amd64`로 빌드 → ECR push → EC2는 `pull`만 합니다.
>
> ⚠️ swap이 2GB가 아니라 1.5GB인 것은 AL2023 기본값을 그대로 쓴 결과입니다.
> 계획서 §2.2는 2GB 기준이었는데, D7 튜닝에서 부족하면 그때 늘립니다.

### swap 확인


### 설치한 것

| 소프트웨어 | 버전 | 설치 |
| --- | --- | --- |
| Docker | AL2023 기본 | `dnf install docker` + `systemctl enable --now` |

`usermod -aG docker ec2-user` 후 **재접속해야** sudo 없이 `docker` 명령이 동작합니다.

> psql 15 클라이언트 ↔ RDS 서버 18 버전 차이 경고가 뜨지만 접속·조회는 정상입니다.

### 아웃바운드 — 왜 제한하지 않나

보안그룹 아웃바운드는 기본값(전체 허용)을 유지합니다. EC2가 외부로 나가야 하는 곳:

- ECR / Docker Hub (`docker pull`)
- `dnf` 패키지 저장소
- Mistral · Gemini API
- Grafana Cloud remote write
- `cs.sogang.ac.kr` (교수 크롤링)
- Let's Encrypt ACME (Caddy 인증서)

대상이 많고 IP가 유동적이라 화이트리스트 관리 비용이 이득보다 큽니다.
**인바운드를 3개로 조인 것으로 충분**하다고 판단했습니다.

### 도메인 — 왜 `nip.io`인가

| 선택지 | 비용 | 판단 |
| --- | --- | --- |
| Route 53 호스팅 영역 | $0.5/월 + 도메인 등록비 | 크레딧 6개월 = $3 — 아깝진 않지만 불필요 |
| 도메인 직접 구매 | 연 $10~15 | 프로젝트 수명(6개월)보다 김 |
| **`nip.io`** | **0원** | ✅ |

`nip.io`는 `<IP>.nip.io` 형태를 그 IP로 해석해 주는 공개 DNS입니다.
`54.180.181.46.nip.io` → `54.180.181.46`. **등록 절차가 없습니다.**

**HTTPS가 되는 이유** — Let's Encrypt가 `nip.io` 도메인에도 인증서를 발급합니다.
Caddy가 기동 시 ACME 챌린지를 자동 수행하므로 인증서 설정이 따로 필요 없습니다.

**제약**
- IP가 도메인에 박혀 있어 **EIP가 바뀌면 도메인도 바뀝니다** → 프론트 재빌드 필요
  (`NEXT_PUBLIC_API_URL`이 빌드 타임 변수, 계획서 §7.3)
- Let's Encrypt rate limit — `nip.io`는 공용 도메인이라 발급 한도를 공유합니다.
  Caddy를 반복 재시작하면 일시적으로 발급이 막힐 수 있습니다

> 실서비스라면 도메인을 사는 게 맞습니다. 여기서는 **6개월 시한부 + 크레딧 보존**이
> 우선이라 `nip.io`를 택했습니다.

## 5. 접속 경로 — DB를 어떻게 쓰나

퍼블릭 액세스가 꺼져 있으니 로컬에서 직접 못 붙습니다. **EC2를 경유**합니다.

```
로컬 PC ──SSH(22)──> EC2 ──5432──> RDS
         (SG-web)          (SG-rds)
```

```bash
ssh -L 5432:seoganpyo-db.czuy88iog7v8.ap-northeast-2.rds.amazonaws.com:5432 ec2-user@<ec2-public-ip>
# 다른 터미널에서
psql -h localhost -p 5432 -U postgres -d seoganpyo
```

**앱은 터널 없이 직접 연결**합니다 — EC2 컨테이너가 이미 VPC 안에 있으므로:

```
DB_HOST=seoganpyo-db.czuy88iog7v8.ap-northeast-2.rds.amazonaws.com
DB_PORT=5432
DB_NAME=seoganpyo
DB_USER=postgres
DB_PASSWORD=<별도 전달>
```

### 데이터 적재 시 (§3, 🟩 민지)

로컬에서 `import_courses.py`를 RDS 상대로 돌릴 때 위 터널을 씁니다. EC2가 아직 없으면 적재가 막히므로, **일정상 EC2 생성이 데이터 적재보다 앞서야** 합니다.

한 겹이 뚫려도 다음 겹이 막습니다.

| 계층 | 수단 | 막는 것 |

## 7. 겪은 문제

### 보안그룹을 시드니 리전에 생성

**증상** — 콘솔에서 SG를 만들었는데 CLI `--region ap-northeast-2` 조회에 안 잡힘.

**원인** — CloudShell/콘솔 리전이 `ap-southeast-2`(시드니)로 설정된 상태에서 생성. 보안그룹은 **리전 종속 리소스**라 서울 EC2·RDS에 붙일 수 없음.

**조치** — 서울에 재생성, 시드니 것 삭제 (SG-rds → SG-web 순서, 참조 관계 때문). 시드니에 EC2·RDS·EIP 잔여 없음 확인.

**재발 방지**
```bash
aws configure set region ap-northeast-2
```
콘솔 우상단 리전 확인을 습관화. 계획서 §2.1에 "다른 리전에 만들고 잊는 것이 과금 사고의 흔한 원인"으로 적어둔 것이 실제로 발생.

→ 포스트모템 상세: `docs/postmortems/` (§8.4)

### 보안그룹 규칙을 "모든 트래픽 + 내 IP"로 설정

**증상** — 첫 설정이 유형 "모든 트래픽", 소스 "내 IP".

**문제** — 웹 서비스가 본인 IP에서만 접속 가능하고, 접속 시 모든 포트가 열림. 의도와 정반대.

**조치** — HTTP/HTTPS는 `0.0.0.0/0`, SSH만 본인 IP로 분리.

### 백업 보존 7일 설정 실패

**증상** — `The specified backup retention period exceeds the maximum available to free tier customers`

**원인** — 무료 플랜 상한이 1일.

**조치** — 1일로 설정. §2.5 백업 훈련을 수동 스냅샷 방식으로 변경(§3).

## 부록 — 용어

| 용어 | 뜻 |
| --- | --- |
| **VPC** | 계정 전용 가상 네트워크. 리전 단위 |
| **서브넷** | VPC를 AZ별로 쪼갠 IP 구간. IGW 라우팅이 있으면 퍼블릭 |
| **IGW** (Internet Gateway) | VPC와 인터넷을 잇는 관문 |
| **NAT Gateway** | 프라이빗 서브넷의 아웃바운드 전용 출구. 시간당 과금 |
| **AZ** (Availability Zone) | 리전 내 물리적으로 분리된 데이터센터 |
| **보안그룹** | 인스턴스 단위 방화벽. 화이트리스트 + 스테이트풀 |
| **스테이트풀** | 인바운드 요청의 응답은 아웃바운드 규칙 없이 자동 허용 |
| **DB 서브넷 그룹** | RDS가 배치될 수 있는 서브넷 목록. 2개 이상 AZ 필요 |
| **Multi-AZ** | 다른 AZ에 대기 인스턴스를 두는 이중화. 비용 2배 |
| **PITR** | Point-In-Time Recovery. 자동 백업 기반 시점 복구 |
