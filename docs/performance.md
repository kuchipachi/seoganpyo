## 1. Docker 이미지 최적화 (D3, 2026-09-24)

### 측정 환경

| 항목 | 값 |
| --- | --- |
| 빌드 머신 | MacBook Pro (Apple M1 Pro) — Docker Desktop 29.7.2, buildx v0.36.1 |
| 타깃 플랫폼 | `linux/amd64` (EC2 t3.micro 기준 — Apple Silicon 에서 에뮬레이션 빌드) |
| 빌드 옵션 | `docker buildx build --no-cache --platform linux/amd64 --load` |
| 공정성 조건 | 베이스 이미지는 미리 받아 둔 상태(pull 시간 제외), 매 빌드 전 BuildKit 컨텍스트 캐시 삭제(`buildx prune --filter type=source.local`) |
| 크기 기준 | `docker image inspect` 의 로컬(비압축) 크기. ECR 에 올라가는 압축 크기는 이보다 작음 |

### 결과

| 이미지 | 크기 before | 크기 after | 변화 | 빌드 시간 before → after |
| --- | --- | --- | --- | --- |
| **api** (backend) | 121.5 MB | **102.3 MB** | **−19.2 MB (−15.8%)** | 52s → **36s (−31%)** |
| ocr | 67.4 MB | 67.4 MB | 변경 없음 | 20s |
| frontend | 64.5 MB | 64.5 MB | 변경 없음 | 67s |
| **합계** | **253.4 MB** | **234.2 MB** | **−19.2 MB (−7.6%)** | |

### 무엇을 바꿨나

| 변경 | 효과 |
| --- | --- |
| backend `Dockerfile` 의 docker-cli 스테이지 삭제 | 이미지 −19.2 MB, 빌드 −16s. prod 는 docker.sock 을 마운트하지 않아 원래 쓸 수 없던 바이너리 (챗 도구는 #10 에서 자동 제외) |
| `frontend/.dockerignore` 커밋 (`.gitignore` 가 `.dockerignore` 를 무시하고 있어 레포에 없었음) | **빌드 실패 방지** — 아래 참고 |
| 루트 `.dockerignore` 신규 (허용 목록 방식) | `.env`·`*.pem` 등 비밀값이 빌드 컨텍스트에 섞이는 것 차단 |

### frontend — `.dockerignore` 가 없을 때 (재현)

`frontend/Dockerfile` 은 `COPY . .` 를 씁니다. `.dockerignore` 가 없는 개발 PC(예: 레포를 새로 받아 `pnpm install` 한 팀원)에서 빌드하면:

| | `.dockerignore` 없음 | 있음 |
| --- | --- | --- |
| 전송 컨텍스트 | **498.67 MB** (호스트 `node_modules` 포함) | 2.61 MB |
| 결과 | ❌ **빌드 실패** — `cannot copy to non-directory: .../node_modules/@radix-ui/react-accordion` | ✅ 성공 |

호스트(macOS)의 `node_modules` 가 deps 단계에서 설치한 Linux `node_modules` 위로 복사되며 충돌합니다. 기존에는 민지 로컬에만 `.dockerignore` 가 있어 드러나지 않았습니다.

### 측정하면서 알게 된 것

- **첫 측정은 불공정했다** — 처음 잰 before 값에는 베이스 이미지 pull 시간이 섞여 있었다(변경이 없는 ocr 이 44s → 19s 로 "빨라짐"). 베이스를 캐시한 뒤 다시 쟀다.
- **컨텍스트 전송량은 캐시 영향을 받는다** — BuildKit 은 같은 빌더에서 이전 컨텍스트와의 차이만 보낸다. 캐시를 지우지 않으면 6 kB 처럼 비현실적으로 작게 찍힌다.
- **루트 `.dockerignore` 의 크기 효과는 작다** (api 컨텍스트 14.57 MB → 13.47 MB) — BuildKit 이 `COPY` 대상 경로만 골라 전송하기 때문. 이 파일의 가치는 크기보다 **비밀값 차단**이다.

## 2. 부하 테스트 — 측정 방법 (결과를 보기 전에 확정, 2026-09-27)

> 튜닝 전후를 **믿을 수 있게** 비교하려고, 결과를 보기 전에 방법·기준·분석 규칙을 먼저 고정한다.
> 근거는 k6 문서, Google SRE Book, Brendan Gregg(USE method, 벤치마킹 체크리스트), Gil Tene(coordinated omission),
> Georges et al.(반복·신뢰구간), 컬리·우아한형제들·LINE 성능 테스트 사례. 출처는 §2.9.

### 2.1 무엇을 알고 싶은가 (가설)

1GiB EC2 에서 컨테이너 메모리 한도 합계(1,536MB)가 물리 메모리(913MB)보다 크다.
→ 부하가 오르면 OOM 이전에 **swap 스래싱으로 지연이 급격히 나빠질 것**이다.
→ 메모리 한도·swap·DB 풀·워커 수를 **한 번에 하나씩** 조정해 이 지점을 뒤로 밀 수 있는지 확인한다.

### 2.2 도구와 부하 모델

| 항목 | 결정 | 이유 |
| --- | --- | --- |
| 도구 | **k6** (v2.3, Apple Silicon 네이티브) | 기존 JMeter 이미지는 amd64 전용 → M1 에서 에뮬레이션 + JVM 5GB. 생성기가 병목이 될 위험 |
| 부하 모델 | **open model** (`arrival-rate`: 초당 도착 수 고정) | closed model(동시 사용자 고정)은 서버가 느려지면 요청도 줄어 꼬리 지연을 과소 측정(coordinated omission) |
| 생성기 병목 판정 | `dropped_iterations == 0`, 목표 RPS ≈ 달성 RPS, Mac load average 기록 | 못 보낸 요청이 숨지 않고 지표로 남음 |
| JMeter | 교차 검증용으로 유지 | 같은 부하에서 두 도구 p95 가 비슷하면 측정 도구 신뢰 근거 |

### 2.3 시나리오 (조회 위주, 1 iteration = 사용자 행동 1회)

| 행동 | 비율 | 요청 |
| --- | --- | --- |
| 홈 화면 | 20% | `GET /` (Next.js, ~9KB) |
| 강의 목록 | 30% | `GET /backend/api/v1/courses?year=2026&semester=1` (~30KB) |
| 강의 검색 | 20% | `GET .../courses?q=<무작위 검색어 13개 중>` |
| 강의 상세 | 20% | `GET .../courses/{무작위 1~37}` + `GET .../syllabus/{id}` |
| 교수 목록 | 10% | `GET .../professors` |

- **제외**: 로그인 필요 흐름(2차에 테스트 계정으로 추가), OCR·강의계획서 요약·관리자 챗(외부 유료 API·호스트 Ollama 의존)
- 정적 자원(JS/CSS 청크)은 제외 — 브라우저 캐시 대상이라 서버 용량과 무관. **한계로 명시**
- 스크립트: `infra/loadtest/k6/seoganpyo.js`

### 2.4 테스트 종류와 합격 기준 (SLO)

| ID | 종류 | 부하 (iteration/초) | 시간 | 목적 |
| --- | --- | --- | --- | --- |
| smoke | 스모크 | 1 | 1분 | 스크립트·환경 검증 (측정 세션마다 1회) |
| **load** | 평상시 부하 | 0→5 램프 1분 + 5 유지 10분 | 11분 | **튜닝 전후 비교의 주 지표** |
| stress | 단계 증가 | 5→10→20→30→40, 단계당 3분 | 15분 | 단계별 p95·자원 변화, 급격히 나빠지는 지점 |
| breakpoint | 한계 탐색 | 1→150 선형 | 최대 20분 + 회복 관찰 5분 | SLO 만족 최대 처리량, swap 포화·OOM 지점, 회복 여부 |

| 대상 | p95 | p99 | 에러율 |
| --- | --- | --- | --- |
| API | < 500ms | < 1,500ms | < 1% |
| 페이지 | < 1,000ms | — | < 1% |

- 기준 500ms = Apdex T (JMeter 대시보드 기본값과 동일)
- **안전장치**: breakpoint 는 에러율 10% 초과가 30초 이어지면 자동 중단 (운영 서버 보호)

### 2.5 서버 쪽 동시 관찰 (USE method)

부하가 도는 **동안** EC2 에서 `scripts/loadtest/collect-server-metrics.sh` 로 수집한다 — "왜 거기서 한계인가"에 답하기 위해.

| 자원 | 도구 | 보는 것 |
| --- | --- | --- |
| CPU | `vmstat 1` | us·sy·**st**(steal), run queue(r) |
| 메모리 | `vmstat 1` | free, **si/so(swap in/out)** |
| 디스크(swap) | `iostat -xz 1` | %util, 대기열 |
| 네트워크 | `sar -n DEV 1` | 처리량 |
| 컨테이너 | `docker stats`(5초), `docker events` | 컨테이너별 메모리, **OOM·재시작** |
| 커널 | `dmesg -w` | OOM killer |
| DB | `pg_stat_activity`(5초) | state 별 연결 수 (RDS 한도 79, 앱 풀 5+10) |
| 설정 증명 | `docker inspect` (전·후) | 적용된 메모리 한도·이미지 ID·재시작 횟수 |
| **인스턴스 크레딧** | CloudWatch `CPUCreditBalance` (5분) | 버스터블 스로틀링 여부 — 소진 시 측정값이 오염됨 (§3.4) |

관측 스택(Prometheus·Loki)은 측정 대상과 1GiB 를 나눠 쓰므로 **측정 중 띄우지 않는다**.

### 2.6 신뢰도 규칙

| 규칙 | 내용 |
| --- | --- |
| 반복 | load 5회, stress 3회, breakpoint 3회 (튜닝 전·최종). 중간 튜닝 변수는 load 3회 + breakpoint 1회 |
| 워밍업 제외 | load 는 앞 120초 제외, stress 는 단계마다 앞 30초 제외 |
| percentile 계산 | Grafana 윈도우 값이 아니라 **raw 샘플**로 계산 (`scripts/loadtest/analyze.py`). percentile 끼리 평균 내지 않음 |
| 여러 회 집계 | 실행별 값의 **중앙값 [최소–최대]** |
| 전후 비교 | 실행 단위 **Mann-Whitney U**(정확 분포, 양측) + 중앙값 변화율의 **부트스트랩 95% CI** |
| 변수 통제 | 한 번에 한 설정만 변경 · 같은 시간대 · 실행 사이 5분 쿨다운 · 가능하면 before/after 교차 순서 |
| 조건 기록 | 매 실행 `conditions.txt`: git 커밋, RTT(TCP connect), EC2 CPU 크레딧, Mac load average |
| 무효 처리 | load 에서 `dropped_iterations > 0` 이면 무효 (생성기가 목표 부하를 못 냄) |

### 2.7 튜닝 변수 (한 번에 하나씩)

| 순서 | 변수 | 가설 |
| --- | --- | --- |
| V1 | 컨테이너 메모리 한도 현실화 (합계 ≤ 약 850MB, api 는 swap 금지) | 스래싱 대신 예측 가능한 성능 또는 명확한 OOM 지점 |

| V3 | DB 풀 `DB_POOL_SIZE`/`DB_MAX_OVERFLOW` | 스레드풀(40)과 풀(15) 불일치로 인한 대기 해소 |
| V4 | uvicorn `--workers 2` | 처리량 ↑ vs 메모리·DB 연결 2배 — 트레이드오프 기록 |

### 2.8 비용·운영 영향

- 데이터 전송(EC2→집): 권장 범위 약 25GB 예상, 월 100GB 무료 한도 내 — 실행마다 누적 기록
- CPU 크레딧: T3 Unlimited — 초과분 약 $1 이내 예상 (크레딧 차감)

## 3. 베이스라인 측정 결과 (튜닝 전, 2026-09-27)

> 조건: §2 방법 그대로. 운영 서버(EC2 t3.micro) 대상, 부하 생성은 민지 Mac(M1 Pro, 충전 중·다른 앱 종료).
> 운영 이미지: ECR `latest` (실행마다 `server/before.txt` 에 이미지 ID 기록) · 측정 도구 커밋 `f511763` · RTT(TCP connect) 평균 15~23ms · EC2 CPU 크레딧 288(최대) · 데이터 수신 누적 4.6GB

| 테스트 | 계획 | 실행 | 비고 |
| --- | --- | --- | --- |
| smoke | 1 | 1 | 통과 |
| load | 5 | **5** | 5회 모두 통과 |
| stress | 3 | **3** | 3회 모두 30~40 iter/s 구간에서 기준 초과 |
| breakpoint | 3 | **1** | 1회차에서 **서비스가 21분간 멈추는 결함** 발견 → 중단 ([포스트모템](postmortems/2026-09-27-db-pool-deadlock.md)) |

### 3.1 평상시 부하 (load, 5 iter/s) — 튜닝 전후 비교의 기준

| 지표 | 5회 중앙값 [최소–최대] | 기준 |
| --- | --- | --- |
| **API p95** | **283ms [279–296]** | < 500ms ✅ |
| API p99 | 371ms [349–597] | < 1,500ms ✅ |
| 페이지 p95 | 114ms [100–121] | < 1,000ms ✅ |
| 처리량 | 6.01 RPS [5.96–6.03] | 목표 ≈ 6 |
| 에러율 | 0% | < 1% ✅ |
| `dropped_iterations` | 0 (5회 모두) | 생성기가 목표 부하를 냄 |

- **측정 노이즈 범위: API p95 기준 17ms** (279–296). 튜닝 후 변화가 이보다 작으면 개선으로 보지 않는다
- **API 별 p95**: 강의 목록 **330–406ms** / 검색 약 156ms / 교수 약 144ms / 상세 약 88ms / 강의계획서 약 62ms
  → 강의 목록 하나가 전체 API p95 를 끌어올림 (§3.4)
- 서버: CPU 평균 약 10%(순간 최대 53%), api 메모리 100MB/512MB, OOM 0, swap 소량, DB 연결 활성 1

### 3.2 단계 증가 (stress, 3회) — 급격히 나빠지는 지점

| 단계 (목표 iter/s) | 달성 RPS | API p95 — 1 / 2 / 3회 | API p99 범위 | 판정 |
| --- | --- | --- | --- | --- |
| 1 (5) | 6 | 269 / 288 / 294ms | 335–476ms | ✅ |
| 2 (10) | 12 | 286 / 295 / 288ms | 377–497ms | ✅ |
| 3 (20) | 24 | 304 / 314 / 333ms | 725–1,199ms | ✅ (p99 흔들리기 시작) |
| 4 (30) | 36 | 338 / **726** / 409ms | 545–2,635ms | ⚠️ 경계 (3회 중 1회 초과) |
| 5 (40) | 35–48 | **929 / 1,189 / 1,412ms** | 1,913–31,954ms | ❌ 3회 모두 초과 |

- **기준을 안정적으로 지키는 부하: 20 iter/s (약 24 RPS)**. 30 iter/s 는 경계, 40 은 초과
- 한계 근처 결과는 매번 흔들림 (1회차는 5단계에서 처리량이 막히고 500·타임아웃, 2·3회차는 지연만 증가) → 단일 측정으로 한계를 말하면 안 되는 이유

### 3.3 한계 탐색 (breakpoint, 1회)

| 분 | 달성 RPS | API p95 | 에러율 |
| --- | --- | --- | --- |
| 1–3 | 6 → 24 | 286–310ms | 0 |
| **4** | **33.2** | 455ms | 0 ← **기준을 지킨 최대 처리량** |
| 5–6 | 42 → **50.6** | 529–762ms | 0 ← 처리량 최대 |
| **7** | **17.9 (붕괴)** | 30,525ms | 2% |
| 8–10 | 12 → 5 | 60,000ms (타임아웃) | 82–85% → 자동 중단 |

- **기준 만족 최대 처리량 약 33 RPS, 절대 최대 약 51 RPS.** 그 이상에서는 처리량이 평평해지는 게 아니라 **1/3 로 붕괴**
- 부하가 끝난 뒤에도 **21분 동안 DB API 가 응답하지 않음** — 원인과 재현은 [포스트모템](postmortems/2026-09-27-db-pool-deadlock.md)

### 3.4 병목 분석 (USE method)

부하 테스트와 **같은 시간대**에 기록한 서버 지표로 추적했다.

| 자원 | 한계 구간(stress 5단계) 상태 | 병목? |
| --- | --- | --- |
| **api CPU** | 컨테이너 **97–114% = 코어 1개 포화** (서버 전체는 평균 46% — vCPU 2개 중 1개만 사용) | ✅ 처리량 한계의 원인 |
| 메모리 | api 130MB/512MB, 여유 약 70MB, OOM 0, 컨테이너 재시작 0 | ❌ |
| swap | si/so 소량 (최대 수천 페이지/단계) | ❌ |
| DB 연결 | **`idle in transaction` 15 = 풀 한도(5+10) 전부 점유**, 로그에 `QueuePool ... timeout 30` | 증상 (교착) |
| steal | 약 1% | ❌ |
| **CPU 크레딧** | 부하 1시간 동안 **288 → 266.8 (7% 소모)**, 최저 266.8 | ❌ |

- **CPU 1코어 포화**: uvicorn 단일 프로세스 + Python GIL → vCPU 2개 중 1개만 쓴다
- **강의 목록 요청 1회 = SQL 64개** (강의 1 + `course_details` 37 + `professor_details` 25, N+1). 응답 변환 단계에서 지연 로딩되며 그동안 DB 연결을 쥔다 → CPU 를 가장 많이 쓰고, 교착의 조건을 만든다
- **인스턴스 스로틀링 아님** (🟦 하연 확인): t3.micro 는 버스터블이라 크레딧이 바닥나면 baseline(2 vCPU 기준 20%)으로 강제 제한되어 측정값이 오염된다. CloudWatch `CPUCreditBalance` 5분 간격 추이를 보면 부하 구간(17:22~18:27)에 288 → 266.8 로 **7%만 소모**했고 이후 회복했다. 즉 **크레딧 소진으로 느려진 게 아니다** — 인스턴스를 키워도 해결되지 않으며, 코드·구성 튜닝이 맞는 방향임을 뒷받침한다
  - 크레딧 1개 = vCPU 1개를 1분간 100% 사용. 1시간에 21개 소모 = 부하 중에도 **CPU 가 대부분 놀았다**는 뜻 → 교착(락 대기)으로 아무 일도 안 하고 기다린 §3.3 과 일치
  - ⚠️ T4(워커 2개)에서는 CPU 사용이 실제로 늘어난다. 같은 지표를 다시 재서 **처리량 ↑ vs 크레딧 소모 ↑** 트레이드오프를 확인할 것
- **처음 가설 기각**: §2.1 가설은 "메모리 한도 합계(1,536MB) > 물리 메모리(913MB) → swap 스래싱이 병목"이었으나, **메모리는 여유 있었고 병목은 CPU(단일 프로세스)와 요청 수용 방식**이었다

### 3.5 튜닝 계획 수정 (측정 결과 반영)

§2.7 의 원래 순서(메모리 한도 → swap → 풀 → 워커)는 기각된 가설에 기반했다. 측정 결과로 다시 짠다 — 여전히 **한 번에 하나씩**.

### 3.6 측정하면서 알게 된 것

- **측정 스크립트 버그 2개로 첫 측정을 버렸다.**
  1. 서버 정상 확인 함수가 `return 0` 없이 끝나 마지막 산술 비교(거짓)의 종료 코드 1을 반환 → 정상을 실패로 오판해 세션이 1분 만에 중단
  2. **ssh 가 백그라운드 수집기의 종료를 기다림** (`chmod && nohup … &` 에서 `&` 가 묶음 전체에 걸려 서브셸이 ssh 출력을 붙잡음) → k6 가 수집 시간(12분)만큼 늦게 시작해 **서버 지표가 부하 없는 구간에 기록**됨. load 1회차 도중 k6 경과 시간이 실제 시간과 어긋나는 것을 보고 발견. 해당 실행은 `results/invalid-ssh-block-20260927` 로 격리하고 처음부터 다시 측정. 이후 실행마다 `collector_started` 와 `k6_started` 를 기록해 **정렬을 검증**
- **자동 중단된 breakpoint 는 수집기보다 먼저 끝난다** — 실행 스크립트가 수집기를 5분만 기다려 회복 관찰 구간을 놓칠 뻔함 → 수집 종료까지 기다리도록 수정
- **부하 생성기 교체가 옳았다**: 기존 JMeter(amd64 에뮬레이션, closed model)였다면 붕괴 구간에서 요청 발생률이 같이 떨어져 **붕괴 자체가 가려졌을 것**이다. open model 에서는 `dropped_iterations` 로 드러났다
- **ICMP 가 막혀 ping 으로 RTT 를 잴 수 없다** → TCP connect 시간으로 대체
- 데이터 전송은 예상(25GB)보다 훨씬 적은 4.6GB — 월 100GB 무료 한도의 약 5%

#### 무엇이 문제였나

9/27 교착에서 서비스가 **21분간 멈췄는데 컨테이너는 `healthy`** 였다.
`/` 가 DB 를 건드리지 않기 때문.

`/healthz`(DB `SELECT 1`)를 만들었으나 **첫 설계(#22)가 교착을 못 잡았다.**
별도 엔진(NullPool)이 막힌 운영 풀을 우회하고, `async def` 라 스레드풀도 안 거쳐
**교착의 두 조건을 모두 피해 갔다.**

#### 측정 결과

같은 교착(강의 목록 60 req/s × 60초 과부하)을 두 버전에 재현.

| 시점 | #22 (NullPool · `async`) | **#24 (`def` + 운영 풀)** |
| --- | --- | --- |
| 평상시 `/healthz` | 200 | 200 |
| **교착 중 `/healthz`** | **200 · 0.02초** ❌ | **타임아웃** ✅ |
| Docker 상태 | `healthy` 유지 | **`unhealthy`** — 과부하 종료 후 28초 |
| 재시작 → API 정상 | (재시작 안 됨) | 22초 |
| **교착 시작 → 복구** | **21분** (9/27 운영) | **약 50초** |

autoheal 검사 주기(15초)를 더해도 최대 약 65초.

> `unhealthy` 전환이 28초로 빨랐던 것은 **과부하 도중 이미 헬스체크가 실패**하기
> 시작해, 종료 시점에 연속 실패 2회가 쌓여 있었기 때문이다.

#### 📊 수치

**과부하 후 복구: 21분 → 약 1분.** 사람 개입 없이 자동 감지·재시작.

21분은 사람이 알아채고 손으로 고친 시간이고, 1분은 **아무도 안 봐도 되는** 시간이다.

#### 알게 된 것

**헬스체크는 실제 요청과 같은 경로를 타야 한다.**
DB 가 살아있는지만 확인하는 것으로는 부족하다. 교착은 DB 가 아니라 **앱 안쪽**
(스레드풀 + 연결 풀)이 막힌 상태이므로, 헬스체크도 그 둘을 거쳐야 같이 막힌다.

**장애 하나를 재현했다고 그 계열 전체가 검증된 것은 아니다.**
DB 네트워크 차단으로는 통과했지만 교착에서는 실패했다. 증상이 비슷해 보여도
**막히는 지점이 다르면 다른 장애**다.

#### ⚠️ T1 과의 상호작용

T1(`--limit-concurrency`)을 적용하면 트래픽이 몰려 한도가 찼을 때 **헬스체크도 503** 을
받는다. 90초(30초 × 3회) 이어지면 autoheal 이 **멀쩡히 버티는 서버를 재시작**해
오히려 용량이 준다.

T1 적용 시 둘 중 하나가 필요하다.

- 헬스체크 재시도·주기를 늘려 **짧은 과부하와 교착을 구분** (교착은 부하가 끝나도 계속됨)
- T1 적용 후 breakpoint 로 **실제 재시작이 일어나는지 측정**

### 4.2 T1 — 동시 처리 한도 (로컬 검증 2026-09-28 · 운영 측정 2026-09-29)

> 목표: 과부하에서 교착 없이 버티고(넘치는 요청은 즉시 503), 부하가 끝나면 즉시 회복.
> 환경: 로컬 재현(`scripts/loadtest/repro/`) — 운영과 같은 api CPU 1코어·512MB, 풀 5+10, **운영과 같은 헬스체크(30초×3회)·autoheal(15초)**.
> 부하: 강의 목록 60 요청/초 (open model) — 짧은 과부하 60초 / 긴 과부하 240초.

#### 두 가지 구현 비교

| | 한도 없음 (현재 운영) | A. uvicorn `--limit-concurrency 15` | **B. 앱 미들웨어 `MAX_CONCURRENT_REQUESTS=14`** |
| --- | --- | --- | --- |
| 교착 (60초 과부하 후) | 교착, **953초** 뒤 회복 | 없음, **즉시** 회복 | 없음, **즉시** 회복 |
| 긴 과부하(240초) 중 헬스체크 | — | **503** (한도가 헬스체크까지 거절) | **200** (한도에서 제외) |
| **긴 과부하 중 autoheal 재시작** | — | **2회** (76초·162초 — 멀쩡한 서버 재시작) | **0회** |
| 성공 요청 (240초) | — | 2,065 (14%) | **12,009 (83%)** |
| **성공 처리량** | — | 약 8.6 RPS | **약 50 RPS** |
| 받아들인 요청 지연 | 60초 타임아웃 | (대부분 즉시 503) | p50 258ms · p95 304ms |

**B 를 채택.**

- **A 의 두 가지 문제**
  1. **헬스체크까지 503** — uvicorn 한도는 경로를 가리지 않는다. 과부하가 90초(30초 × 3회) 넘게 이어지자 autoheal 이 **버티고 있던 서버를 재시작**했고, 재시작 동안 처리 용량은 0 이 됐다. T3(자동 복구)와 T1 이 서로를 방해한 것
  2. **연결 수를 센다** — `--limit-concurrency` 는 "connections or tasks" 를 센다. 브라우저·k6 는 연결을 재사용(keep-alive)하므로 **놀고 있는 연결도 한도를 차지** → 서버에 여유가 있어도 거절. 같은 한도에서 성공 처리량이 B 의 1/6
- **B 의 설계** (`app/concurrency.py`)
  - **처리 중인 요청만** 센다 (응답 전송 완료까지 — 응답 변환 단계에서도 DB 연결을 쥐므로)
  - 한도 = **풀(5+10) − 1 = 14** → 처리 중 요청이 모두 연결을 받을 수 있어 교착 불가 + **헬스체크용 연결 1개 여유**
  - `/healthz` · `/` · `/metrics` 는 한도에서 **제외** → 과부하 중에도 헬스체크 200 → autoheal 이 오작동하지 않음. DB 다운이면 여전히 실패 → 자동 복구 유지
  - 거절 응답은 `503` + `Retry-After: 1` + 프론트 `request()` 가 읽는 구조화 에러(`SERVER_BUSY`)
  - 풀 크기를 바꾸면 한도도 같이 바꿔야 한다 (`docker-compose.prod.yml` 주석)

#### 정정 — 강의 목록 처리 능력

포스트모템에 "거절률 86% 는 처리 능력(약 8~10 RPS)을 넘기 때문"이라고 적었으나 **틀렸다.** 원인은 A 의 연결 수 계산이었다.
B 에서 동시 14개 · 응답 0.26초 → 리틀의 법칙으로 약 54 RPS, 측정 약 50 RPS. **강의 목록 처리 능력은 약 50 RPS** (CPU 1코어, T2 적용 전).

> ⚠️ **이 표의 절대 수치는 가벼운 응답 기준이다.** 재현 DB 에 `course_details`·`professor_details` 가 비어 있어 응답이 15KB 였다 (운영 130KB).
> 운영 응답을 복사해 크기를 맞추고 다시 재면 **T1 단독 처리 능력은 약 44 RPS** (60 요청/초에서 성공 73%, CPU 97%) — §4.3.

| DB 풀 타임아웃 (`QueuePool`) | 분당 80건 | **0건** |
| DB `idle in transaction` 최대 | 15 (전부, 교착) | 14 (= 한도, 교착 없음) |
| **부하 종료 → 회복** | **21분** | **5초 이내** (k6 중단 10:06:37 → 다음 탐침 10:06:41 에 200) |
| `/healthz` · autoheal 재시작 | healthy 인데 서비스 불가 · — | 과부하 내내 **200** · **0회** |
| api CPU (포화 구간) | — | 약 98% — CPU 1코어가 다 쓰일 때까지 일함 |

#### 📊 수치

**과부하 후 서비스 중단 21분 → 0분.** 한계를 넘어도 처리량이 무너지지 않고 약 54 RPS 를 유지하며, 넘치는 요청만 즉시 거절한다.

#### 알게 된 것

- **부하가 낮을 때도 503 이 조금 났다** (15~24 RPS 에서 0.5~1.6%). 평균 동시 처리는 2~3개지만 요청이 몰리거나 일부가 느려지는 순간(p99 1.2초) 14개를 넘었다.
  한도 14 는 교착을 막는 상한(풀 15)에 맞춘 값이라 올릴 수 없다 → **순간 몰림을 흡수하는 것은 요청당 처리 시간을 줄이는 T2 의 몫**
- 기준 만족 최대 처리량(33 RPS)은 그대로다. T1 은 **처리 능력을 올리는 튜닝이 아니라 무너지지 않게 하는 튜닝**이다. 처리 능력은 T2 에서 측정
- 로컬 재현의 T1 단독 처리 능력(약 44 RPS, 강의 목록만)과 운영 성공 처리량(약 54 RPS, 혼합 시나리오)은 시나리오가 달라 직접 비교하지 않는다

### 4.3 T2 — 강의 목록 N+1 제거 (로컬 검증 2026-09-28 · 운영 측정 2026-09-30)

> 목표: 강의 목록 요청 1회의 SQL 64개 → 3개. 요청당 CPU·DB 연결 점유 시간을 줄여 **처리 능력**을 올린다.
> 환경: 로컬 재현 — api CPU 1코어·512MB, 풀 5+10, T1 한도 14. **응답 크기를 운영과 같게(130KB)** 맞춤 (아래 ⚠️).
> 방법: 이미지·도착률 조합을 **3라운드 번갈아** 60초씩. 실행마다 이미지 태그·응답 크기를 확인.
> 원본: [`results/repro-local-20260928-t2/`](../infra/loadtest/k6/results/repro-local-20260928-t2/)

#### 무엇을 바꿨나

`CourseResponse` 는 `course.details`, `professor.details` 까지 직렬화한다. 목록 쿼리는 `joinedload(Course.professor)` 만 해서
**응답 변환 중 강의·교수마다 지연 로딩 쿼리**가 나갔다 (강의 37 + 교수 25 + 본 쿼리 등 = 64개).

```python
query = db.query(Course).options(
    joinedload(Course.professor).selectinload(Professor.details),
    selectinload(Course.details),
)
```

`selectinload` 는 `IN (...)` 쿼리 한 번으로 묶어 불러온다 → **3개**. 응답은 **바이트 단위로 동일** (수정 전후 130,356 bytes).
회귀 방지: `tests/test_course_list_queries.py` — SELECT 수를 세어 강의 수와 무관하게 3개 이하인지 확인
(강의 3·20개, 검색 경로). 수정 전 코드에서는 6·29·15개로 실패.

#### 결과 — 같은 도착률에서 (3라운드 평균)

| --- | --- | --- | --- |
| **20 요청/초** p50 | 22.2ms | **12.7ms** | **−43%** |
| 20 요청/초 p95 | 24.6ms | **14.9ms** | −39% |
| 20 요청/초 api CPU | 33% | **19%** | −42% |

| 60 요청/초 (과부하) | T1 단독 | **T1 + T2** |
| --- | --- | --- |
| 거절(503) | **27%** (라운드별 25.8·28.1·27.0%) | **0%** |
| 성공 처리량 | 약 44 RPS | **60 RPS (전부)** |
| p95 | 352ms | **8.0ms** |

#### 📊 수치

**강의 목록 처리 능력 약 44 → 약 158 RPS (약 3.6배)** — CPU 1코어 포화 기준, 로컬 재현.
에러 1% 미만을 지키는 최대치로 봐도 **약 44 → 약 150 RPS**. 쿼리 64 → 3개.

요청 하나당 api CPU 로 환산하면 약 22ms → 약 6ms (포화 CPU ÷ 처리량). DB 는 별도 컨테이너이므로 이것은 **앱 쪽 비용**이다 —
쿼리 하나마다 드는 SQLAlchemy·드라이버 처리가 61번 사라졌다. 병목이 앱 CPU 1코어라는 베이스라인 분석(§3.4)과 맞는다.

#### ⚠️ 측정하면서 알게 된 것 — 재현 데이터가 가벼웠다

1차 비교는 재현 DB 에 `course_details`·`professor_details` 가 **비어 있는** 상태였다 (PDF 시드는 강의만 넣음).
응답이 15KB — 운영(130KB)의 1/9 — 라 직렬화 비용이 빠져 **처리량을 부풀려 잰다.**
수정 전후 응답이 같아 결과만 보고는 알 수 없었고, 응답 내용을 열어 보고 발견했다.

- 운영 공개 API 를 1회 조회해 details 를 재현 DB 에 복사 (`scripts/loadtest/repro/seed-details-from-prod.py`) → 130KB 로 맞추고 **전부 다시 측정**
- 1차 결과는 [`light-payload/`](../infra/loadtest/k6/results/repro-local-20260928-t2/light-payload/)에 격리 — 방향(개선)은 같음
- 같은 이유로 §4.2 T1 의 "약 50 RPS" 도 가벼운 응답 기준이었다 → 운영 크기로는 **약 44 RPS**

**지연은 같은 도착률끼리만 비교할 수 있다.** 같은 T2 이미지가 20 요청/초에서 12.7ms, 60 요청/초에서 6.6ms 로
**부하가 높을 때 더 빨랐다.** 이미지를 바꿔 교차 측정(`result-t2x-*`)해 보니 이미지가 아니라 도착률을 따라갔다 —
노트북(Docker Desktop)의 CPU 절전 상태 영향으로 보인다. 포화 처리량은 CPU 를 끝까지 쓰므로 이 영향이 없어 **대표 수치로 처리 능력을 쓴다.**

- 41~51 RPS 에서 1~2% 거절이 잠깐 났다가 60~69 RPS 에서 다시 0% 가 됐다. 순간 몰림은 부하 크기만으로 정해지지 않는다.
  "기준 만족 최대 처리량" 은 §2 에서 미리 정한 대로 **마지막으로 기준을 지킨 구간**으로 계산했다 (베이스라인·T1 도 같은 방식)
- breakpoint 한 번에 수신 2.9GB — 처리량이 늘어난 만큼 측정 전송량도 늘었다 (월 100GB 무료 한도 관리, §2.8)

### 5.2 읽을 점

**RDS 가 절반 이상이다.** 데이터는 거의 없는데(강의 37건) 비용의 56% 를 차지한다.
RDS 요금은 **데이터 양이 아니라 인스턴스 가동 시간** 기준이기 때문이다 — 1MB 를
담든 10GB 를 담든 같다.

→ 줄이려면 **가동 시간**을 줄여야 한다. 최대 7일까지 중지할 수 있고, 중지 중에는
스토리지 비용만 나간다 (§2.5 중지 전략).

**퍼블릭 IPv4 가 9.8%** 다. 2024년부터 연결 여부와 무관하게 과금된다.
EIP 를 쓰지 않아도 EC2 에 공인 IP 가 붙는 한 발생한다.

**ECR 은 거의 0** 이다. 수명주기 정책(최근 3개 보존)이 작동하고 있다.
