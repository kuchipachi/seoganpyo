## 근본 원인

**서버가 요청을 무제한으로 받는데, 요청 하나가 스레드풀을 두 번 거치며 그 사이 DB 연결을 쥐고 있다.**

### 요청 하나가 거치는 경로 (강의 목록 API)

`def get_courses(...)` 는 동기 함수라 FastAPI 가 **스레드풀(AnyIO 기본 40개)** 에서 실행한다.

1. **스레드 ①** — API 함수 실행: `db.query(Course).options(joinedload(Course.professor)).all()` → DB 연결을 풀에서 빌림
2. 함수가 ORM 객체를 반환하면 FastAPI 가 `response_model` 로 검증·변환한다. 동기 엔드포인트라 **이것도 스레드풀(스레드 ②)** 에서 돈다
3. 변환 중 `course.details`, `professor.details` 에 접근 → **지연 로딩 쿼리 62개** (강의 37 + 교수 25). 이 동안 **같은 DB 연결을 계속 쥐고 있다**
4. 응답을 보낸 뒤에야 `get_db` 가 세션을 닫아 연결이 반납된다

요청 1회에 나가는 SQL (로컬 DB 로그로 계수):

| 쿼리 | 횟수 |
| --- | --- |
| `FROM courses` (+ professors join) | 1 |
| `FROM course_details` | **37** |
| `FROM professor_details` | **25** |
| 합계 (`SELECT 1` pre-ping 포함) | **64** |

### 교착이 생기는 과정

1. 과부하로 요청이 쌓인다. uvicorn 은 **받을 수 있는 만큼 전부 받는다** (동시 처리 한도 없음)
2. 스레드 ① 을 마친 요청은 **DB 연결을 쥔 채** 스레드 ② 를 기다린다 — 연결 풀 크기만큼(15개) 쌓임 → `idle in transaction` 15개
3. 스레드 40개는 새로 들어온 요청들의 ① 단계가 차지하고, 연결이 없으니 **30초씩 기다린다**
4. 연결을 가진 요청은 스레드를 못 받고, 스레드를 가진 요청은 연결을 못 받는다 → **교착**
5. 30초 풀 타임아웃으로만 조금씩 풀린다: 스레드 40개 × (60초 ÷ 30초) = **분당 80건 타임아웃** — 관찰값과 정확히 일치
6. 클라이언트는 60초에 이미 떠났지만, 서버는 쌓인 수천 건을 30초씩 실패시키며 소진 → **21분 뒤에야 회복**

### 왜 자동으로 감지·복구되지 않았나

- Docker 헬스체크가 `GET /` (DB 를 쓰지 않음)만 확인 → DB API 가 전부 죽어도 `healthy`
- 그래서 `restart: unless-stopped` 도 동작하지 않음
- 알림 체계(Grafana Alerting·CloudWatch)는 D9~D10 예정이라 미구축

## 원인을 찾은 과정 — 가설 → 반증 → 수정 → 검증

운영 서버를 다시 멈추지 않도록 **로컬 Docker 에서 운영과 같은 조건**(api CPU 1코어·512MB, 단일 uvicorn, 풀 5+10, 같은 데이터 37강의)으로 재현했다.
모든 실험은 같은 과부하(강의 목록 60 요청/초 × 60초) 후 회복 시간을 쟀다.

### 1) 재현 — 운영과 같은 패턴

| | 운영 (EC2) | 로컬 재현 |
| --- | --- | --- |
| 교착 중 DB 상태 | `idle in transaction` 15 | `idle in transaction` 15 |
| 풀 타임아웃 | 분당 80건 | 분당 80건 |
| 부하 종료 후 회복 | 약 21분 | 953초 (약 16분) |

### 2) 첫 가설 — "스레드풀(40) > 연결 풀(15) 이라 생기는 교착" → **반증**

첫 가설은 "스레드가 연결보다 많아서 서로 기다린다"였다. 그렇다면 **풀을 스레드보다 크게(45)** 하면 사라져야 한다.

| 설정 | 교착 중 DB 상태 | 풀 타임아웃 | 회복 |
| --- | --- | --- | --- |
| 풀 5+10 | `idle in transaction` 15 | 분당 80건 | 953초 |
| **풀 45+0** | **`idle in transaction` 45** | **분당 80건** | **606초** |

**여전히 교착.** 그리고 스레드는 40개인데 **연결 45개가 전부** 묶였다 — 연결을 쥔 요청이 스레드 **밖**에서 기다린다는 뜻.
→ 풀 크기는 원인이 아니다. 풀을 키우면 교착이 더 많은 연결을 묶을 뿐이다.

### 3) 수정 가설 — "요청을 무제한으로 받는 구조 + 스레드풀 2단계 사용"

연결을 쥔 채 스레드 ② 를 기다리는 요청이 **몇 개든 쌓일 수 있는 게** 문제라면, **동시에 처리하는 요청 수를 연결 풀 이하로 제한**하면 처리 중인 요청은 모두 연결을 받을 수 있어 교착이 생길 수 없다.

### 4) 검증 — 동시 처리 한도 (`uvicorn --limit-concurrency 15`, 풀 5+10 그대로)

| 설정 | 부하 중 p95 | 부하 중 실패 | 풀 타임아웃 | **회복** |
| --- | --- | --- | --- | --- |
| 한도 없음 (운영) | 60초 (타임아웃) | 30% | 분당 80건 | **953초** |
| **한도 15** | **37ms** | 86% (**즉시 503 거절**) | **0건** | **0초** |

**교착 소멸, 부하가 끝나는 즉시 정상.** 받은 요청은 37ms 에 처리하고, 넘치는 요청은 기다리게 하지 않고 곧바로 503 으로 돌려보낸다.
~~거절률 86% 는 이 부하(60/초)가 처리 능력(강의 목록 약 8~10 RPS)을 크게 넘기 때문~~ — **틀린 해석 (2026-09-28 정정)**.
uvicorn `--limit-concurrency` 는 처리 중인 요청이 아니라 **연결 수**("connections or tasks")를 센다. k6·브라우저는 연결을 재사용(keep-alive)하므로
놀고 있는 연결까지 한도를 차지해 서버에 여유가 있어도 거절했다. 처리 중 요청만 세는 앱 미들웨어로 같은 한도를 걸자
성공 처리량이 약 8.6 → 약 50 RPS 로 올랐다 (동시 14 ÷ 응답 0.26초 ≈ 54, 리틀의 법칙과 일치). 강의 목록 처리 능력은 약 50 RPS 다
(재현 DB 의 details 가 비어 응답이 가벼웠던 값 — 운영과 같은 130KB 응답으로는 약 44 RPS, [performance.md §4.3](../performance.md)).
→ T1 은 uvicorn 플래그가 아니라 앱 미들웨어로 구현 ([performance.md §4.2](../performance.md)).

## 재발 방지

| # | 조치 | 목적 | 상태 |
| --- | --- | --- | --- |
| 1 | **동시 처리 한도** — 앱 미들웨어(`MAX_CONCURRENT_REQUESTS` = 풀 − 1, 헬스체크 제외). uvicorn 플래그는 연결 수를 세고 헬스체크까지 거절해 기각 | 교착 원천 차단, 과부하 시 즉시 503 (load shedding) | T1 — 로컬 검증 완료 |
| 2 | 강의 목록 **N+1 제거** (`selectinload(Course.details)`, `selectinload(Professor.details)`) | 쿼리 64 → 약 3, 요청당 CPU·연결 점유 시간 감소 → 처리량 증가 | 튜닝 2순위 |
| 3 | **헬스체크에 DB 확인** 추가 | 같은 장애 시 `unhealthy` → 자동 재시작 | 예정 |
| 4 | 풀 대기 시간 단축 (`DB_POOL_TIMEOUT` 30 → 수 초) | 보조 — 교착이 생겨도 빨리 풀리게 | 검토 |
| 5 | 5xx 비율 알림 (Grafana Alerting, D10) | 사람이 즉시 인지 | 예정 |

각 조치는 **한 번에 하나씩** 적용하고 같은 부하 측정으로 효과를 확인한다 ([performance.md §2.7](../performance.md)).

## 배운 것

- **"healthy" 는 아무것도 보장하지 않았다.** 포스트모템 1호(홈 200 만 보고 배포 성공 판단)와 같은 교훈이 컨테이너 헬스체크에서 반복됐다. 헬스체크는 서비스가 실제로 하는 일(DB 조회)을 확인해야 한다.
- **처음 가설이 틀렸다.** "스레드가 연결보다 많아서"라는 그럴듯한 설명을 실험 한 번이 뒤집었다. 풀을 키우는 쪽으로 바로 고쳤다면 교착이 더 많은 연결을 묶는 상태로 배포됐을 것이다.
- **처음 세운 성능 가설(메모리·swap 병목)도 틀렸다.** 측정해 보니 메모리는 여유 있었고 CPU 1코어와 요청 수용 방식이 문제였다. 튜닝 순서를 측정 결과로 다시 짰다.
- **과부하에서 서버는 "느려지는" 게 아니라 "무너질" 수 있다.** 받을 수 없는 요청은 빨리 거절하는 편이 모두에게 낫다.
- **부하 측정이 운영 장애를 먼저 찾았다.** 수강신청 기간에 실사용자가 먼저 겪었을 문제다.
