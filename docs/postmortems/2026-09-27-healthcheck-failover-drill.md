# DB 헬스체크 · 자동 복구 검증 (장애 주입 훈련)

> 작성: 2026-09-27 · 🟦 하연
> 성격: **계획된 훈련** — 실제 장애가 아니라 복구 체계가 동작하는지 확인하려고 일부러 일으킴
> 관련: [교착 장애](2026-09-27-db-pool-deadlock.md)(원인 제공) · PR #22(대응) · 튜닝 계획 T3

## 왜 했나

[2026-09-27 교착 장애](2026-09-27-db-pool-deadlock.md)에서 서비스가 **21분간 멈췄는데도**
컨테이너는 계속 `healthy` 였다. 두 가지 결함이 있었다.

| 결함 | 내용 |
| --- | --- |
| 헬스체크가 DB 를 안 봄 | `/` 는 JSON 한 줄을 돌려줄 뿐 DB 를 건드리지 않는다 |
| 자동 복구 수단 없음 | `restart: unless-stopped` 는 **프로세스가 죽었을 때만** 동작. 살아서 멈춘 상태는 방치 |

PR #22 로 `/healthz`(DB `SELECT 1`)와 autoheal 을 넣었다.
**만들었다고 동작하는 게 아니므로** 장애를 주입해 확인했다.

## 주입 방법

RDS 보안그룹(`SG-rds`)에서 EC2(`SG-web`) 허용 규칙을 제거해
**앱은 살아있고 DB 만 닿지 않는** 상태를 만들었다. 교착과 증상이 같다.

```
EC2 콘솔 → 보안 그룹 → SG-rds → 인바운드 규칙 → PostgreSQL 5432 삭제
```

관찰은 EC2 에서 5초 간격으로:

```bash
while true; do
  printf '%s  http=%s  %s\n' "$(date +%T)" \
    "$(curl -s -o /dev/null -w '%{http_code}' https://54.180.181.46.nip.io/backend/healthz)" \
    "$(docker inspect seoganpyo-api --format '{{.State.Health.Status}} restarts={{.RestartCount}}')"
  sleep 5
done
```

## 타임라인

| 시각 | 상태 | 경과 | 비고 |
| --- | --- | --- | --- |
| 14:44:47 | `200 healthy` | — | 정상 |
| **14:44:52** | **`503 healthy`** | **0s** | DB 차단 → **즉시 감지** |
| 14:46:29 | `503 unhealthy` | **+97s** | 30초 × 3회 실패 후 전환 |
| **14:46:46** | **`502 starting`** | **+114s** | **autoheal 이 재시작** |
| ~14:49:10 | — | — | DB 규칙 복구 (콘솔에서 5432 재허용) |
| 14:49:14 | `200 starting` | — | DB 응답 재개 → 헬스체크 통과 시작 |
| 14:49:19 | `200 healthy` | — | 정상화 (규칙 복구 후 **약 9초**) |

**감지 즉시 → 자동 복구 착수까지 약 2분.** 이전에는 21분간 아무 일도 일어나지 않았다.
DB 가 살아난 뒤에는 **9초 만에** healthy 로 돌아왔다 — 사람이 재배포할 필요가 없었다.

## 확인된 것

**① 헬스체크가 DB 장애를 감지한다**
`/healthz` 가 차단 직후(5초 관찰 주기 내) 503 을 반환했다.
같은 상황에서 기존 `/` 는 200 을 냈을 것이다.

**② 응답 지연으로 타임아웃 설정이 동작함을 확인**
차단 후 관찰 간격이 5초 → 8초로 늘었다. `/healthz` 가 DB 연결을 기다렸다 실패하기
때문이며, `connect_timeout=3` 이 실제로 적용되고 있다는 증거다.
운영 풀(`pool_timeout=30`)을 썼다면 판정이 30초씩 밀렸을 것이다.

**③ autoheal 이 unhealthy 컨테이너를 재시작한다**
`unhealthy`(14:46:29) → `starting`(14:46:46), **17초 만에 개입**. 설정한 15초 주기와 일치.

**④ 근본 원인이 남아 있으면 복구되지 않는다**
DB 가 계속 막혀 있는 동안 컨테이너는 `starting` 에 머물렀다(14:46:46~14:49:13, 약 2분 27초).
헬스체크를 통과하지 못해 기동을 마치지 못한 것이다.
**자동 복구는 일시적 고장에는 듣지만 원인 자체를 고치지는 않는다.**

## 예상과 달랐던 것

### `RestartCount` 가 0 그대로였다

재시작이 일어났는데도 `docker inspect` 의 `RestartCount` 는 0 이었다.

이 값은 **Docker 자체 restart 정책**(`restart: unless-stopped`)이 재시작한 횟수만 센다.
autoheal 은 외부에서 `docker restart` 를 호출하므로 집계되지 않는다.

→ **`RestartCount` 만 보고 "재시작 없었다" 고 판단하면 안 된다.**
실제 증거는 `State.Health.Status` 가 `starting` 으로 바뀌는 것, 그리고 autoheal 로그다.

### `starting` 상태에서 이미 200 을 반환한다

14:49:14 에 `http=200` 인데 컨테이너는 아직 `starting` 이었다(→ 14:49:19 healthy).
헬스체크가 **연속 성공 횟수를 채워야** healthy 로 바뀌기 때문이다.

즉 **컨테이너 상태보다 실제 서비스 복구가 먼저다.** 상태만 보고 "아직 죽었다" 고
판단하면 실제보다 장애 시간을 길게 잡게 된다.

### 502 가 뜨는 구간이 있다

재기동 중에는 Caddy 가 백엔드에 붙지 못해 502 를 반환한다(14:46:46~14:49:09).
사용자에게는 503 이 아니라 502 로 보인다 — 알람 룰을 만들 때 **두 코드를 모두** 봐야 한다.

## 배운 것

**"healthy" 는 무엇을 확인했는지 알아야 믿을 수 있다.**
헬스체크가 보지 않는 것은 장애가 나도 드러나지 않는다. 이번 교착이 그 사례였다.

**자동 복구를 만들었으면 일부러 고장 내서 확인해야 한다.**
설정을 넣는 데는 30분이 걸렸지만, 실제로 동작하는지는 주입해 보기 전까지 알 수 없었다.
확인 과정에서 `RestartCount` 가 안 올라간다는 사실도 알게 됐다 — 이걸 모르고 실제 장애를
겪었다면 "autoheal 이 동작 안 했다" 고 오판했을 것이다.

**복구 자동화는 원인 규명을 대체하지 않는다.**
DB 가 막힌 동안은 몇 번을 재시작해도 복구되지 않았다.
자동 복구는 **일시적 고장에서 사람이 개입할 시간을 벌어주는 것**이지 해결책이 아니다.
