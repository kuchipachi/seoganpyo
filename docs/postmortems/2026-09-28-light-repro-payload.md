## 근본 원인

**재현 환경이 운영과 "같다"고 확인한 항목에 데이터 모양이 빠져 있었다.**

재현 환경을 만들 때 운영과 맞춘 것은 CPU 1코어·메모리 512MB·단일 uvicorn·DB 풀 5+10·**강의 37개** 였다.
강의는 강의계획서 PDF 시드(`seed_courses_from_syllabi.py`)로 넣었는데, 이 스크립트는 **강의 행만** 만든다.
운영에서 강의 목록 응답을 무겁게 만드는 두 테이블은 다른 경로로 채워진다.

| 테이블 | 운영에서 채우는 경로 | 재현 DB |
| --- | --- | --- |
| `course_details` (개요·평가 방법·AI 추천 문구) | 시드 `--summarize` (Ollama 요약) | **0행** |
| `professor_details` (연구 분야·AI 연구 요약) | 교수 크롤링 `crawl_and_upsert` | **0행** |

강의 수(37)가 같으니 "같은 데이터"라고 여겼지만, 응답 크기는 **1/9**(15KB vs 130KB) 이었다.
강의 목록은 CPU 1코어가 병목(§3.4)인 엔드포인트라 **직렬화(Pydantic 변환·JSON 인코딩)할 양이 1/9** 이면 처리량이 부풀려진다.

### 왜 바로 알아채지 못했나

1. **수정 전후 응답이 똑같았다.** T2 는 "응답을 바꾸지 않는다"가 성공 조건이라, 두 이미지의 응답이 바이트까지 같은 것을 보고 오히려 안심했다. 둘 다 비어 있어서 같았던 것이다
2. **N+1 쿼리는 데이터가 없어도 나간다.** 지연 로딩은 행이 없어도 강의·교수마다 쿼리를 보낸다. 쿼리 수 테스트(64 → 3)는 통과했고, 수정 전후 차이도 뚜렷해서 "제대로 재고 있다"는 인상을 줬다
3. **결과의 방향이 기대와 맞았다.** 틀린 수치였지만 "T2 가 빠르다"는 결론은 같았다. 기대와 맞는 결과는 의심받지 않는다 — 이상 신호가 **방향이 아니라 크기**(3배 부하에서 더 빠름)로 드러나고서야 열어 봤다

### 부수 결함 ① — 이미지가 바뀌지 않은 측정 (02:23)

수정 전 이미지로 바꾸는 compose 파일(`compose.dev24.yml`)을 **임시 폴더에만** 만들고, 레포 폴더에서 compose 를 실행했다.
파일을 찾지 못한 채 기존 컨테이너로 측정이 돌아 "수정 전"과 "수정 후"가 다른 이미지가 아니었다.
결과 파일에 이미지 태그를 찍고 있었기에 발견했다 → 이후 **실행마다 `docker inspect` 로 이미지를 확인하고 다르면 중단**하도록 바꿨다.

### 부수 결함 ② — 낮은 부하에서 더 느린 지연 (03:10)

데이터를 맞춘 뒤에도 "같은 T2 코드가 20 요청/초에서 12.7ms, 60 요청/초에서 6.6ms" 가 남았다.
이미지와 도착률을 엇갈려 측정하자 이미지가 아니라 **도착률**을 따라갔다 (`t1t2` 20/초 12.7ms = `t2` 20/초, `t2` 60/초 6.6ms = `t1t2` 60/초).
노트북(Docker Desktop)이 한가하면 CPU 가 절전 상태로 내려가는 영향으로 판단했다.
→ **지연은 같은 도착률끼리만 비교**하고, 대표 수치는 CPU 를 끝까지 쓰는 **포화 처리량**으로 정했다.

## 즉시 조치

- 운영 공개 API(로그인 불필요한 강의 목록)를 1회 조회해 details 를 재현 DB 에 복사 — `scripts/loadtest/repro/seed-details-from-prod.py`. 운영 DB 에는 접속하지 않음
- 응답 크기를 운영과 맞춘 뒤 **모든 비교를 다시 측정** (4개 이미지 × 3라운드 교차 + 처리 한계)
- 가벼운 데이터 결과는 삭제하지 않고 [`light-payload/`](../../infra/loadtest/k6/results/repro-local-20260928-t2/light-payload/) 에 격리하고 이유를 README 에 적음
- 이미 기록된 T1 "약 50 RPS" 를 지우지 않고 **정정 주석**을 붙임 — PR #27 본문, performance.md §4.2, 교착 포스트모템

## 배운 것

- **"같은 데이터"는 행 수가 아니라 응답이 같아야 한다.** 강의 37개를 맞추고 안심했지만, 성능을 좌우한 것은 그 강의에 딸린 텍스트였다. 재현 환경은 **측정하려는 대상의 비용을 만드는 요소**(여기서는 직렬화할 양)가 같은지로 검증해야 한다
- **기대와 맞는 결과일수록 한 번 열어 본다.** 세 번의 결함 모두 결론의 방향은 맞았다. 이상 신호는 크기에서 나왔다 — "개선됐다"가 아니라 "너무 많이 개선됐다"
- **틀린 수치는 지우지 않고 정정한다.** 이미 PR·문서에 나간 "약 50 RPS" 를 조용히 고치면 왜 바뀌었는지 아무도 모른다. 취소 대신 정정 주석과 격리 폴더로 남겼다
- **로컬 배수도 그대로 옮길 수 없다.** 데이터를 맞춘 로컬 3.6배도 운영에서는 2.1배였다. 로컬은 강의 목록만, 운영 시나리오는 강의 목록이 약 1/4 이다. 튜닝 효과는 **실제 트래픽 구성**에서 재야 한다
- 교착 포스트모템(1호)의 "처음 가설이 틀렸다"와 같은 교훈이 측정 쪽에서 반복됐다 — **측정 도구와 환경도 검증 대상**이다
